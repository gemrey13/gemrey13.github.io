# Content Rules — codewithgem Portfolio

## Truthful Content Principle

The design can be ambitious. The content must remain truthful.

NEVER invent:
- Employers
- Clients
- Events
- Achievements
- Awards
- Certifications
- Testimonials
- Project metrics or outcomes
- Professional experience
- Personal interests
- Locations
- Contact information

If content is missing, leave an intentional placeholder for Gem to provide later. Placeholders should be clearly marked in the code (comments or TODO markers) so they are easy to find and fill in.

## Projects

### Presentation Philosophy
- Projects are case studies, NOT cards in a grid
- Each project tells a story: what, why, the problem, what was built, technologies, challenges, the result
- Large, immersive project presentations
- Do not present all projects identically — each can have its own visual personality

### Project Detail Structure
When a visitor enters a project, possible structure:
1. The problem
2. The idea
3. The architecture
4. The interesting technical challenges
5. The solution
6. The result

The exact structure varies by project. Not every project needs every section.

### Key Projects

**Gi-Recon PRO**
- Reconciliation system involving POS, Grab, and Foodpanda data
- Demonstrates: business software, data processing, reconciliation, automation, desktop applications, database systems, performance optimization, real-world problem solving
- Present as a serious engineering project

**BIR eJournal**
- Business-oriented application involving automation, data management, auditing, and reporting
- Present as a real-world software project

Do not invent additional details, metrics, or outcomes for these projects. Present what is provided.

## Work Experience

- Career story, not a resume timeline
- Each experience reveals: role, organization, period, responsibilities, technologies, notable work
- Professional and structured
- Separate from Events
- Do not invent employers or roles

## Events — "Where I've Shown Up"

- This is NOT work experience
- Events, conferences, meetups, workshops, hackathons, tech gatherings, communities
- Title: "WHERE I'VE SHOWN UP"
- More personal and visual than Work Experience
- Each event may include: name, date, location, type, participation, description, photos, certificates, links
- Do not invent events
- Photos (when provided) should be an important part of the storytelling
- Possible visual directions: interactive timeline, event wall, photo collage, visual journal, map-based storytelling, scrapbook-style

## Blog — "Things I've Learned the Hard Way"

- Real experiences, not generic tutorials
- Potential topics: software engineering lessons, reconciliation systems, Electron development, performance optimization, legacy systems, DBF processing, worker threads, automation, AI-assisted development, freelancing, debugging, architecture decisions, things that broke, lessons from real projects
- Do not fabricate articles
- Structure should make it easy to add articles later
- Blog post content will be provided by Gem

## Toolkit

- Technologies presented as tools used to build things
- NOT skill percentage bars or generic "React — 90%" indicators
- Could be interactive: selecting a technology reveals projects where it was used
- Technologies include: React, TypeScript, JavaScript, Next.js, Node.js, Python, Django, Flask, FastAPI, PHP, Electron, SQLite, PostgreSQL, MySQL, Supabase, Firebase, AWS, React Native, Tailwind CSS, AI/LLM technologies
- Only include technologies that accurately represent actual experience

## The Lab

- Title: "THE LAB"
- Subtitle: "Experiments. Prototypes. Things that probably shouldn't work."
- Content: experimental interfaces, animation experiments, 3D experiments, AI experiments, WebGL, creative coding, automation, prototypes
- More experimental in visual treatment than the rest of the portfolio
- Communicates curiosity
- Lab experiments will be provided/built by Gem

## More Than Just a Developer

- Scroll-driven storytelling with large typography
- Volleyball is part of this storytelling section — not a separate standalone section
- Content comes from Gem's actual information
- Do not invent personal details

## Profile Photo

- Gem will provide the photo
- Integrate meaningfully — not a circular avatar
- Possible: editorial image, full-bleed, masked, subtle motion, layered composition, interactive reveal
- Possible locations: hero, personal introduction, "More Than Just a Developer", contact

## CV

- Gem will provide the actual CV
- Portfolio must have clear VIEW CV and DOWNLOAD CV options
- Easy to find without making the site feel like a resume
- Do not generate or invent CV information

## Developer Mode

- Optional hidden/secondary experience
- Reveals technical info about the site: framework, language, router, animation, rendering, status
- Can reveal playful info: current page, animation state, system status, component info, performance
- Default experience remains clean — Developer Mode is opt-in

## Contact

- Use Gem's actual contact information
- Do not invent contact details
- Include actual: GitHub, LinkedIn, email, social links
